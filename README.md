# hl-douyin-plugin

TRSS-Yunzai 抖音自动续火插件。定时给抖音好友发消息保住火花，跑完把结果推到群里，配套一个带临时验证码鉴权的 Web 面板做可视化管理。

移植自 `douyin-auto-spark`（Playwright / TypeScript），改写为 Yunzai 插件：浏览器自动化换成仓库里已有的 puppeteer，定时改成可热更新的 cron，账号按机器人隔离，Cookie 加密落盘。

## 特性

- **定时续火** — 6 位 cron（秒在最前），锅巴或指令改完立即生效，不用重启
- **跳过今日已续火** — 抖音火花一天只认一次，已成功的账号定时任务直接跳过，可开关
- **好友改名不断火** — 续火目标存 `主名 + 别名 + 备注`，主名搜不到自动试别名，命中后把新名提为主名
- **结果推送** — 跑完自动发群 / 私聊 / 两者，支持多群、跨机器人、详细/简要两种模式、仅失败时推送
- **Web 可视化面板** — 账号管理、给指定好友手动发信、拉取会话列表、扫码登录、改配置、看状态与审计
- **私信聊天** — 面板里点一个账号就进它的抖音私信，像 IM 一样收发；聊天记录存本机 sqlite，**不过期**
- **远程过验证** — 抖音扫码后追加身份验证时，私信一个临时链接，在里面看着那台浏览器的画面直接点/拖/打字把验证过掉
- **三种登录方式** — 扫码自动抓 Cookie、私聊粘贴、发 txt 文件（QQ 输入框会截断超长 Cookie）
- **多机器人隔离** — 账号按 botId 分文件存储，面板会话只能进入「你是主人」的那些机器人
- **锅巴配置** — 全部配置项都在锅巴面板里可视化编辑，账号与 Cookie 也在里面增删
- **文本出图** — 帮助 / 设置 / 状态渲染成图片，渲染失败自动降级成文字
- **访问频次控制** — 拦截图片/字体/埋点请求、缓存 Cookie 检查结论，减少对抖音的请求量
- **退出自动收尾** — `#重启` 与进程退出前先关浏览器、聊天页、扫码页、数据库，不留孤儿 Chromium
- **插件更新** — `#抖音更新` 拉取新代码并自动重启，更新前备份 `config/` 与 `data/`

## 安装

在 Yunzai 根目录执行：

- gitee

``` bash
git clone --depth 1 https://gitee.com/fox-glaze/hl-douyin-plugin ./plugins/hl-douyin-plugin
```

然后重启 Yunzai。

无需 `npm install`：依赖全部复用 Yunzai 自带的 puppeteer / express / node-schedule / yaml / lodash，插件自己不引入新包。聊天记录用 Node 内置的 `node:sqlite`，也不算新依赖，但它要 **Node ≥ 22.5**；低于这个版本时聊天功能照样能用，只是不落盘（看不到本地历史），其余功能完全不受影响。

装好后 `#抖音更新` 就能拉取新代码并自动重启，不必再手动 `git pull`。

首次启动会自动生成：

- `config/config.yaml` — 只存你改过的项，默认值在代码里，插件升级后新字段自动补齐
- `data/secret.key` — AES-256-GCM 主密钥（0600），**丢了等于所有 Cookie 作废，备份时别漏**
- `data/accounts/<机器人QQ>.json` — 加密后的账号数据
- `data/chat.db` — 聊天记录（sqlite，WAL 模式），第一次进聊天界面时才建
- `data/audit.json` — 操作审计

整个 `data/` 已在 `.gitignore` 里。

| `#抖音账号` | 主人 | 账号列表、绑定的好友、上次结果 |

| `#抖音状态` | 所有人 | 状态面板，默认出图 |
| `#抖音设置` | 主人 | 查看当前配置与可改项，默认出图 |

#抖音设置 调试 开/关              # 每一步都记日志，卡住时先开它再跑一次

## 续火好友与改名自愈

好友改名是断火最常见的原因，所以续火目标不是一个裸昵称，而是 `{ 主名, 别名[], 备注 }`：

- **主名** — 当前用于搜索的名称（抖音里的备注名优先于昵称）
- **别名** — 历史名 / 备用名，主名搜不到时按顺序试；命中别名会自动把它提为主名，下次直接用新名搜
- **备注** — 只用于展示（「表妹」「同事老王」），不参与搜索

三处都用同一套文本语法，指令、面板、锅巴写法一致：

```text
张三                    # 只有主名
张三(表妹)               # 带备注，全角括号与 ｜ 也认
张三三=张三              # 主名「张三三」，别名「张三」
张三三=张三=小三(表妹)    # 多别名 + 备注
```

旧版本的 `targetNames: ["张三"]` 在读盘时就地迁移成新结构，升级插件不需要任何手动操作。

## Cookie 传输方式

QQ 输入框会截断超长文本，而抖音的完整 Cookie 常常超过限制——贴进去就是残缺的。四条路径按可靠性排序：

1. **扫码** `#抖音登录` — 浏览器自动抓，最省事。要求短信验证的号用 `#抖音自动登录`（见下节）
2. **文件** `#抖音文件登录 账号名` + 发 txt — Cookie 很长时用这个。收到后解析完立刻删除临时文件（`security.deleteCookieFile`）
3. **锅巴 / Web 面板** — 「抖音账号与 Cookie」里一张卡片一个账号，粘 Cookie、配续火好友、开停用都在同一处
4. **粘贴** `#抖音手动登录 账号名 Cookie` — 短 Cookie 直接贴

第 2、4 条只能私聊。群里出现 Cookie 视为泄露：插件会尝试撤回并要求私聊重发。

## 自动过短信验证

异地登录、有风控标记的号扫完码常会再插一道「身份验证 → 接收短信验证码」。这一步里唯一
只有你能提供的东西是那几位数字，点按钮完全可以让插件代劳——`#抖音自动登录` 就是这条路：

1. 照常发二维码，你用抖音 App 扫码确认
2. 抖音弹出身份验证时，插件自己点「接收短信验证码」→「发送验证码」
3. 确认页面上真的出现了倒计时或「验证码已发送」之后，**私信**你一句「请把验证码发给我」
4. 你把短信里那几位数字直接发回来（可以带前后几个字，只取数字），插件填进页面并提交
5. 凭证落进 cookie jar 就算成功——和扫码登录同一条成功路径

要点：

- **不发任何链接**。全程只在私信里要一串数字，公网地址一次都不用露面，比远程操作页面更适合用公网 IP 直连的机器
- **只对短信验证有效**。滑块、拼图、要求绑定手机号、以及抖音改版后按钮找不到的情况，都会自动落回「远程过验证」那条路（下一节）
- **不会白要验证码**。点完「发送验证码」后必须在页面上读到倒计时或「已发送」字样才通知你，避免按钮点空了你却干等短信
- **填错能再填**。抖音报「验证码错误」时会原样告诉你并继续等下一条，不用重新扫码
- 等待上限跟 `security.verifyTimeout`（默认 10 分钟），够你收短信
- 想让 `#抖音登录` 也走这条路，把 `security.autoSms` 打开（或 `#抖音设置 自动短信 开`）。默认关是因为它会真往你绑定的手机发一条短信，`#抖音登录` 的用户未必预期这件事；`#抖音自动登录` 显式打开，不看这个开关

## 锅巴里管账号

锅巴面板第一节「抖音账号与 Cookie」是个可增删的卡片列表，一张卡片就是一个抖音账号：

| 字段 | 说明 |
| --- | --- |
| 账号名称 | 指令与推送里指代这个账号，同一机器人下不能重名 |
| 机器人QQ号 | 账号归哪台机器人管，留空 = 当前在线的第一台。改这里等于把账号搬到另一台机器人下 |
| 账号ID | 只读，保存时生成。改账号名时靠它认出改的是哪一个 |
| Cookie 现状 | 只读，显示「已配置/已失效/未配置」与更新时间 |
| 粘贴 Cookie | **留空 = 不修改**。填了就替换，必须含 `sessionid`，格式不对当场报错 |
| 续火好友 | 顿号分隔，语法与指令一致（`主名=别名(备注)`） |
| 该账号的消息模板 | 留空则用全局模板 |
| 启用 / 备注 | 关掉则定时续火跳过该账号，账号与 Cookie 都保留 |

要点：

- **Cookie 永不回填**。面板是浏览器里的页面，回填就意味着密文随接口发到前端。所以那一栏打开永远是空的，只想改好友时不必重新粘一遍
- **删卡片 = 删账号**。删掉卡片并保存，该账号连同它的 Cookie 一起没了，不可恢复
- 账号数据不在 `config.yaml` 里，而在 `data/accounts/<机器人QQ>.json`（Cookie 为 AES-256-GCM 密文）。锅巴这一节直接读写它，与指令、Web 面板改的是同一份数据
- 校验先做完再落盘：某一行的 Cookie 格式或占位符写错，整次保存回滚，不会留下改一半的状态

`security.allowManualCookie` 关闭时这一栏拒绝写入（与 `#抖音手动登录` 同一开关）。

## Web 面板

发 `#抖音web` 后：**私信**发一条点开即进的链接，群里那条回复只是「指令收到了」（默认连主机与端口一起打码）。

链接形如 `http://host:port/douyin/#ABCD`，验证码放在 URL 的 **hash** 里：hash 不发给服务端，因此不进 access log、不随 Referer 外泄（Yunzai 的 `serverHandle` 会把 `req.query` 整个打进日志，而日志经常被直接贴出来排查问题——码要是写成 `?ABCD` 就跟着贴出去了）。前端读完立刻 `replaceState` 抹掉，地址栏、书签、截图里都不留。同一条私信里也给出地址与 6 位码，链接点不开时可以手输。

流程：点链接（或手输验证码）→ 选择要操作的机器人 → 进入控制台（账号与发信 / 私信聊天 / 抖音登录 / 定时与推送 / 状态与审计）。

「定时与推送」标签页与锅巴改的是同一份 `config/config.yaml`，保存后定时任务立刻重新注册。

安全设计：

- 仅主人可触发；验证码只对「你是主人」的那些机器人授权，选别的机器人返回 403 并记审计
- 验证码一次性、默认 5 分钟过期，服务端只存 sha256，比较走 `timingSafeEqual`
- 验证码通过只换到一个会话，**不等于拿到机器人权限**——必须再显式选机器人，且不能越过授权名单
- 会话 Cookie 为 HttpOnly + SameSite=Strict，Path 限定在挂载路径下
- 验证码提交有独立限流桶（默认 60 秒 8 次），失败累计触发永久拉黑（重启或 `#抖音设置 解封IP` 清空）
- 所有敏感操作写审计，面板里可查
- 私信发送失败时自动作废刚发的验证码

面板默认挂在 Yunzai 自身端口的 `/douyin`。反代到公网时把 `web.url` 填成对外地址。`web.port` 填非 0 会额外起一个独立服务（端口被占用只警告，不影响插件加载）。

## 私信聊天

面板里点一个账号的「进入聊天」，就进它的抖音私信：左边会话列表、右边气泡流、下面输入框，和 IM 一样收发。

### 会话不过期

聊天记录存在 `data/chat.db`（sqlite，WAL 模式），**只增不减，没有任何过期清理**。抖音自己的会话列表只显示最近若干条、往下滚才加载更多，所以本地列表是「并」而不是「覆盖」：远端有的更新预览与时间，远端没有的原样留着——三个月没联系的人仍然在你的列表里。

不用 redis 也不用 `Bot.getMap()`：前者重启就没了，后者（LevelDB）打开时会把整表读进内存。也没塞进 `data/accounts/*.json`，那是「整文件读 → 改 → 整文件覆写」的模型，追加一条消息要把该机器人名下所有账号连 Cookie 密文一起重新落盘一次，而聊天天然并发（用户在点、前端在轮询、页面在收新消息），read-modify-write 丢更新是必然。

`node:sqlite` 要 Node ≥ 22.5。取不到时整块降级成「不落盘」：聊天界面照样能开、能收发，只是没有本地历史，面板上会标出原因，不影响插件其它功能。

### 一个账号同一时刻只能干一件事

聊天页和续火抢**同一把账号锁**（`lib/spark.js` 的 `acquire`/`release`）。同一份 Cookie 同时活在两个 BrowserContext 里，抖音看到的是两个并发登录——掉线和触发验证都从这里开始。所以正在续火的账号点不进聊天，反之定时续火撞上开着的聊天会话会直接报「该账号的聊天窗口正开着」而不是硬闯。

抢锁发生在开浏览器**之前**：抢不到就直接告诉你是谁占着，不白启动一个 Chromium。

### 空闲 180 秒自己收摊

聊天页是常开的，这让 `spark.browserIdleClose` 那套机制失效——`lib/browser.js` 收浏览器的判据是「还有没有非 `about:blank` 的真实页面」，聊天页开着它永远不触发，Chromium 会一直占着 200~400MB 直到 Yunzai 重启。而用户关掉网页并不会通知服务端，只能按「多久没人来轮询」判，所以聊天会话有自己的空闲计时（`chat.idleCloseSec`，默认 180 秒 = 前端漏掉 60 次轮询）。给这么宽是因为重开一次要十几秒，切出去看条视频再回来不该被强制重连。

会话状态机是 `opening → ready → closed`，刻意**不自动重连**：重连要重新抢锁、重开浏览器，那是十几秒和一次新登录会话，该由用户点一下决定。前端拿到 409 就知道会话不在了（`400/500` 是这次操作本身失败、会话还在），提示重新进入。

### 其它几处取舍

- **消息没有 id**。抖音不给，页面上也没有结构化时间，所以一条消息的身份只能是「谁说的 + 说了什么 + 页面上那个时间戳」。去重靠「已存尾部」与「刚读到这一屏」求最长重叠后缀，对「连发两条一样的话」是保守的（第二条会被当重复丢掉）——重复插入是不可逆的污染，漏掉的那条下次刷新还在。
- **发完立刻入库**，不等下一轮轮询把它从页面上读回来：字数回读过、Enter 也确认发下去了，此时前端就该看到自己发的话。下一轮真读到它时重叠去重会认出是同一条。
- **删账号连记录一起清**。删的时候先关掉它的聊天会话再删数据——否则账号没了而会话还挂着一个 Chromium 和一把锁，而锁的 key 是 `botId:accountId`，再没人来 release 它。
- **`/api/state` 不回库的磁盘路径**。只报「可用与否 / 存了多少条」，路径进前端等于把服务器目录结构写进 HTML。
- **审计只记条数**：`chat.send` 记账号、对方、字数，不记内容。

不想要就 `#抖音设置 聊天 关`，或把 `chat.enable` 设为 `false`：面板上入口消失、接口一律 403，已开的会话立刻收掉，**已存的记录不删**。

## 退出与重启时的收尾

`#重启`、`#关机`、以及进程正常退出之前，插件会先把自己的东西收干净：摘掉定时任务 → 并行关掉扫码会话与聊天会话 → 关浏览器 → 关聊天数据库。每步有独立预算（关页面合计 4 秒、关浏览器 6 秒、关库 1 秒），超时只记一行日志继续往下走——你正盯着 `#重启`，一个卡住的 `page.close()` 不该把重启变成「机器人没反应」。

这不是顺手做的整洁工作，是修一个真实存在的泄漏：`#重启` 在服务器上走 `process.execve` 原地换进程镜像，exit 钩子一个都不跑，于是 puppeteer 自己挂的清理不触发，每次重启多留一个 Chromium（200~400MB）和一个 `~/.cache/puppeteer_dev_chrome_profile-*` 目录，而 pid 不变、从外面看「重启成功了」。现场数据：服务器攒到 31 个 profile 目录（最老的来自 2025-10-09），本地 `%TEMP%` 也有 10 个。为什么只漏这一条路、以及为什么不自己去挂信号，见「实现取舍」里的那一节。

「热重载」这条路不用管：本插件有 `index.js`，loader 见到它只 push 并 continue，不注册文件监听。改了 `lib/*.js` 要生效只能 `#重启`。

## 远程过验证

抖音在扫码确认后有时会追加一道身份验证（短信验证码 / 滑块）。这道验证必须由人在浏览器里点，而浏览器是无头的、跑在服务器上——插件的做法是把那个页面的**交互通道**转发给人，而不是自己去破解。

> 如果抖音给的是**短信验证码**，优先走上一节的 `#抖音自动登录`：那条路连链接都不用发，只跟你要几位数字。这一节是给滑块、拼图、以及没见过的验证形态兜底的。

触发时：插件**私信**发起指令的那个人一个临时链接（外加一张现场截图），链接**绝不会出现在群里**。点开就能看到那台浏览器的实时画面，在图上点、按住拖、用输入框打字，和自己操作浏览器一样。验证过掉后 Cookie 照常落进同一个浏览器上下文，插件的主循环查到 `sessionid` 就自动保存——页面上会显示「登录成功」。

页面只支持人在浏览器里能做的物理动作：点击、双击、拖动、滚动、打字、以及 `Enter`/`Backspace` 等七个功能键。**没有执行任意脚本的入口**（那等于把远程代码执行开在公网上，而过一道验证根本不需要它）。

安全边界（与主面板完全隔离）：

- 链接**只私信**，不进群；发不出去就当场作废该链接
- 票据只能操作**这一次登录的那一个页面**：选机器人、增删账号、改配置、看审计一个都做不到，页面里也没有任何通往主面板的入口
- token 走 URL 的 hash（`/douyin/verify#t=xxx`）：hash 不发给服务端，不进 access log、不进 Referer；前端读完立刻 `replaceState` 抹掉，地址栏里也不留
- 接口只认请求头里的 token（`X-Verify-Token`），不接受 query——query 会被写进日志
- 默认绑定首次访问的 IP（`security.verifyBindIp`），链接被转发到别的机器就失效
- 猜 token 与猜面板验证码走同一套失败计数，累计到 `web.banAfter` 次拉黑该 IP
- 登录会话一结束票据即收尾（只留 1 分钟让页面读到「Cookie 已保存」这个结论）；同一次登录重复进验证态会作废旧链接，不会有多个同时有效
- 全程审计：`verify.issue` / `verify.open` / `verify.ip.denied` / `verify.close`。**只记操作次数，不记操作内容**——用户输进去的可能是短信验证码
- `#抖音web下线` 一并作废在外面飘的验证链接，**并终止还在进行的登录会话**（关掉那个浏览器页面）；`#抖音设置 会话` 可以看还有几个

不想用就把 `security.remoteVerify` 关掉，回到「报出验证类型 + 给文件登录/显形浏览器两条替代方案」的老路。

### 浏览器开几个、活多久

- **一个 Chromium 实例，全插件共用**。不是每个用户一个，也不是每个账号一个。账号隔离靠 `BrowserContext`（`createBrowserContext`，老版本退到 `createIncognitoBrowserContext`）：每个抖音账号一个上下文，Cookie 互不污染，但共享同一个浏览器进程。
- **一次登录 = 一个页面**。两个人同时扫码就是两个页面、两个上下文，仍然只有一个浏览器。
- **验证会话到点会自己收摊**。`security.verifyTimeout`（默认 10 分钟）到点后关页面、关上下文、撕票据；主动 `#抖音web下线` 也是同一条清理路径，且不会再推那句「验证没有完成」。
- **页面全关完之后浏览器实例也会被收掉**，延时 `spark.browserIdleClose` 秒（默认 60）。延时是为了跨过续火在两个账号之间的间隔——那时页面已经关了但马上还要再开，立刻关掉会变成每个账号都重启一次浏览器。
- **聊天页是这条规则的例外**。它常开着，于是上面那个「还有没有真实页面」的判据永远成立，浏览器永远不会被收。所以聊天会话有自己的空闲计时（`chat.idleCloseSec`，默认 180 秒），见「私信聊天」一节。
- **进程退出与 `#重启` 之前一定会关掉**，见「退出与重启时的收尾」一节。

### 会话列表为什么要缓存

面板「可视化发信」里那个好友名单，真拉一次要开浏览器、进聊天页、等会话渲染完，好友多的号十几秒；而好友名单几天都不会变一次。所以默认按 `spark.friendsCacheTTL`（240 分钟）缓存在账号 json 里，面板打开发信卡片直接读缓存，点「重新拉取」才真去抖音要一遍。

三处刻意的取舍：

- **空结果不写缓存**。拉到 0 个多半是页面没渲染完或 Cookie 半失效，缓存下来等于把一次偶发失败固化成几小时的「这个号没有好友」。
- **换 Cookie 时作废缓存**。同一个账号名换一份 ck 很可能换的是另一个抖音号（反复扫码时尤其常见），那份名单就是上一个号的好友，列错名字比多等一轮真拉贵得多。
- **`/api/accounts` 不外发名单，只给「几条 + 什么时候拉的」**。那是最多 200 个好友昵称，而这个接口是面板每次刷新都调的；要名单走 `/api/accounts/:id/friends` 单独取。

## 安全说明

- Cookie 以 AES-256-GCM 加密存储，密钥在 `data/secret.key`（不用配置里的口令，因为口令会显示在锅巴面板上，密钥文件不会）
- 接口与日志里的 Cookie 一律打码
- 账号名、好友名进文件名前过滤，`../` 和盘符冒号都会被清掉
- 账号数据按机器人分文件，跨机器人读、删、跑都会失败
- 验证码、会话、IP 封禁全在内存里，**重启即全部失效**——对「主人临时开一次面板」的场景，这是安全收益
- 远程验证链接与面板是两套权限：链接只私信、只能操作那一次登录的页面、默认绑 IP、token 走 hash 不进日志，详见「远程过验证」一节
- 聊天记录明文存在本机 `data/chat.db`（已 gitignore）。这是刻意的：加密就没法用 SQL 翻页和去重了，而它和 Cookie 的性质不同——Cookie 泄露等于账号被接管，聊天记录泄露的范围止于这台机器。不想留就 `#抖音设置 聊天 关` 并删掉那个文件。审计里只记「谁给谁发了几个字」，不记内容

## 常见问题

**搜不到好友** — 用抖音里显示的备注名（备注优先于昵称）。对方改名时给目标加个别名（`#抖音加好友 账号名 新名=旧名`），下次搜到哪个都算命中；真删好友才会报「搜索不到」。

**Cookie 频繁失效** — 抖音单账号多端登录会互相挤掉。`#抖音检查cookie` 能确认；失效的账号在面板和状态图上标红，重新扫码即可。检查结论默认缓存 30 分钟，想立刻重查把 `spark.cookieCheckTTL` 调成 0。

**Cookie 粘不全** — QQ 输入框会截断超长文本。改用 `#抖音文件登录 账号名` 发 txt。

**二维码一直不出 / 报「90 秒内没等到二维码」** — 出码慢的原因几乎都不是风控，是页面太重。未登录访问首页会被抖音带到 `/jingxuan`，HTML 1.6MB、几十张图、推荐流视频还在后台解码，抖音自己的 passport 链（`ttwid/check` → `login_guiding_strategy` → `get_client_cert` → `challenge` → `get_qrcode`）要和它们抢渲染进程主线程，慢机器上实测排队 46 秒才走到 `challenge`。插件现在拦掉推荐流数据源与埋点（passport 链有白名单永不拦，见 `lib/browser.js` 的 `ALWAYS_ALLOW_PARTS`），等码上限给到 90 秒，并且**从二维码真正到手那一刻才开始算 `security.qrLoginTimeout`**——出码慢不再吃掉你的扫码时间。报错里会带「探了 N 轮，最慢一轮 X ms」：单轮超过 1 秒就是主线程被占满的证据，重试一次通常就能出码，实在不行退回 `#抖音文件登录 账号名`。

**报「未出现登录面板」** — 连面板都没等出来，二维码那一步还没轮到。报错里已经带了那一刻的页面现状（title / url / HTML 字节数 / img 数 / 一小段正文）和「点过登录入口」还是「连登录入口都没找到」的区分，先看这两处：HTML 只有几 KB、正文是 `Please wait...`，说明还停在抖音的跳转中间页（插件现在会先等它过掉再等面板，最多等 20 秒）；HTML 正常大小但找不到登录入口，多半是抖音改了面板文案。想看得更细就 `#抖音设置 调试 开` 再扫一次，日志里会有每一步的结果；`#抖音设置 快照 开` 还会把整页截图与 HTML 存进 `data/debug/`，改选择器时对着它看。绕过去的办法是 `spark.headless` 改成 `false` 亲眼看一眼，或退回 `#抖音文件登录` / 手动导入 Cookie。

**扫码确认了但插件没反应，最后说超时** — 先看是哪一种。若停在「已收到扫码」：抖音的二维码约每 60 秒作废一张，页面会自己换新码，但 QQ 里发出去的那张图不会更新，扫作废的码永远等不到结果；插件现在检测到换码就补发一张新图并注明「上一张已过期」。若已经回过「已确认登录，正在取凭证」：抖音在扫码后追加了一道**身份验证**——实测截图里是一个标题为「身份验证」的弹窗，副标题「为保障账号安全，请先完成身份验证，以确保为本人操作」，下面两个选项「接收短信验证码」「发送短信验证」，二维码已被它整块盖掉。

这道验证必须由人来配合，但不用你亲自去服务器，也不一定要点开链接：

- **抖音给的是短信验证码** —— 用 `#抖音自动登录` 重新登一次。插件自己点「接收短信验证码」→「发送验证码」，确认页面上出现倒计时之后**私信**跟你要那几位数字，你发回来它自动填进去提交。全程不发任何链接，详见上面的「自动过短信验证」一节。
- **滑块、拼图、或没见过的形态** —— 插件会认出它，然后**私信**给你一个远程操作链接（外加一张现场截图），点开就能看着那台浏览器的画面把验证过掉，Cookie 照样自动保存，详见「远程过验证」一节。

两条路都会把等待上限自动放宽到 `security.verifyTimeout`（默认 10 分钟），够你收短信。

两条都关掉（`security.remoteVerify` 关、且没用 `#抖音自动登录`）的话，还是老两条路：

1. **改用 `#抖音文件登录 账号名`** ——在你自己的浏览器里登录抖音，验证一次就过，把 `document.cookie` 存成 txt 私聊发过来
2. **把 `spark.headless` 改成 `false` 再扫一次** —— 浏览器窗口会显形在跑 Yunzai 的那台机器上，你自己在里面把身份验证过掉。这条路要求你能看见那台机器的桌面

**从头到尾停在「等扫码」，最后报「N 分内未完成扫码」，但你确实扫了也确认了** — 用的是旧代码，`#抖音更新` 拉一下即可。扫码状态靠拦 `check_qrconnect` 的响应判断，旧版把主机名和 `/passport/web` 前缀一起写进了匹配条件，抖音把这套接口搬到别的子域之后一条都拦不到：二维码还能从 DOM 里捞出来，所以出码、扫码这两步看不出异常，但之后所有状态都不会再变，最后按「等扫码超时」判死，验证链接自然也发不出来。现在判据只留接口名，且**认验证界面这一步完全不依赖任何接口**——每 2 秒直接看页面（连续两轮认出同一种才算，避免撞上首页推荐流的视频标题），所以状态卡在「等扫码」一样会发链接；判死之前还会再看最后一眼，认出来就改成发链接而不是报超时。

**远程验证页打开了、画面也在刷新，但点画面没反应** — 先看画面下方那行小字（「16:20:31 点击 0.547,0.506 已送达远端」）。它是这个页面唯一能区分三种故障的地方：

- **一个字都没出现** → 浏览器压根没派发手势事件。旧版本按「有没有 `window.PointerEvent`」挑一套事件监听，而 QQ 内置浏览器里存在「构造函数有、事件不发」的组合，于是整块画面点下去毫无反应也没有任何报错。现在 pointer / touch / mouse 三条链路一起挂并互相去重，末尾还有一层 `click` 兜底，`#抖音更新` 拉一下即可。
- **写着「已送达远端」但画面不变** → 请求到了服务端、`page.mouse` 也点下去了，是抖音那个弹窗没响应。`#抖音设置 调试 开` 后日志里会有 `[调试] 远程验证 动作 click 相对 0.547,0.506 → 像素 700,405 视口 1280x800`，对着截图核一下像素落点对不对。
- **写着「失败：…」** → 括号里就是原因。「登录会话已结束」= 那次登录已经收尾（多半已经成功了）；「验证链接无效或已过期」= 票据过期或换了 IP，见下一条。

**远程验证链接打不开 / 一进去就说「验证链接无效或已过期」** — 三种可能：链接过了 `security.verifyTimeout`（默认 10 分钟）；被转发到了另一台设备（默认绑定首次访问的 IP，`security.verifyBindIp` 可关）；或者手机在 4G 与 WiFi 之间切换换了 IP——后者把 `security.verifyBindIp` 关掉即可。另外 `web.url` 必须填成对外可达的地址，否则链接里是内网 IP。

**页面打开了却什么都没有 / 标题是「验证码中间页」** — 无头 Chromium 的默认 UA 带 `HeadlessChrome`，抖音见到就返回一个 4KB 的验证码中间页，既没有登录入口也没有聊天列表。插件已在建页时把 UA 里的 `HeadlessChrome` 换成 `Chrome`，遇到这条说明用的是旧代码，`#抖音更新` 拉一下即可。

**报 `createBrowserContext is not a function`** — 装的是 puppeteer v22 之前的版本。插件已带兼容层自动退回旧 API，遇到这条说明用的是旧代码，`#抖音更新` 拉一下即可。

**配了群却没推送** — 先看 `push.target`：选了「仅群」时好友列表不收，反之同理。`#抖音状态` 的「推送范围」一栏就是当前生效值。

**聊天界面里看不到历史，只有这次开着期间的消息** — 落盘层没起来。Node < 22.5 就没有 `node:sqlite`，聊天照样能用但不落盘；`#抖音状态` 与面板上都会写出原因（磁盘只读、`data/` 被占也会导致同样的结果）。升 Node 到 22.5 以上即可，已经发生过的那段对话补不回来。

**点「进入聊天」报「该账号正在续火」/ 定时续火报「该账号的聊天窗口正开着」** — 这是设计如此，不是 bug。聊天和续火抢同一把账号锁：同一份 Cookie 同时活在两个浏览器上下文里，抖音看到的是两个并发登录，掉线和触发验证都从这里开始。等对方那件事结束，或者点「退出聊天」把会话收掉。

**聊天开着一会儿就说「会话已关闭，请重新进入」** — 空闲超时到了（`chat.idleCloseSec`，默认 180 秒）。网页关掉、切后台、或者手机休眠都会让前端停止轮询，服务端只能按「多久没人碰」判。嫌短就把它调大，代价是那段时间里 Chromium 一直占着 200~400MB。刻意不做自动重连：重连要重新抢锁、重开浏览器，十几秒加一次新的登录会话，该由你点一下决定。

**重启之后服务器上多出一个 Chromium 进程 / `~/.cache` 里攒了一堆 `puppeteer_dev_chrome_profile-*`** — 旧代码，`#抖音更新` 拉一下。原因是 `#重启` 走 `process.execve` 原地换进程镜像，exit 钩子一个都不跑，puppeteer 自己挂的清理因此不触发。现在插件在 execve 之前先把浏览器收掉，见「退出与重启时的收尾」一节。已经留下的那些孤儿进程要手动 `kill`，那几个 profile 目录直接删。

**改了 `lib/*.js` 没生效** — 这个插件不参与热重载（有 `index.js` 的插件 loader 不注册文件监听），必须 `#重启`。

**改了 cron 没生效** — 不需要重启。插件自己持有定时任务，锅巴/面板/指令保存后会立刻重新注册；`#抖音状态` 里的「下次执行」就是当前生效的时间。

**面板打不开** — 检查 `web.enable`；反代后确认 `web.url` 填的是对外地址；`#抖音设置 解封IP` 可以解掉误触发的封禁。

**出图失败** — 会自动降级成文字，不会吞掉回复。想固定发纯文字就 `#抖音设置 渲染 关`。

**上面都对不上号，想知道到底停在哪一步** — `#抖音设置 调试 开`（或锅巴「排查」一节）再跑一次，Yunzai 日志里每一步都有一行 `[调试]` 前缀的记录：页面打开的 HTTP 状态、等的元素出没出现、拦到的接口与状态码、每轮验证探测的结论、状态流转、搜索命中的是主名还是别名。Cookie 的值一个字符都不会进日志，只记条数与名字。要连页面长什么样一起留证就再开 `#抖音设置 快照 开`，截图 / 纯文本 / 完整 HTML 按步骤编号存进 `data/debug/`（单页 HTML 常有一兆多，超过 `debug.keep` 个文件自动删最旧的）。查完记得关掉——调试日志会让日志量成倍增长。

## 实现取舍

**为什么不用 `plugin.task` 做定时** — loader 只在插件加载时读一次 `task.cron`，锅巴改完必须重启才生效。所以自己持有 `schedule.scheduleJob`，改配置后 `reschedule()` 立刻换表。

**为什么不复用渲染器的浏览器** — `renderers/puppeteer` 那个实例带自己的重启/超时策略，还会通过 redis 里的 wsEndpoint 跨进程共享。续火与扫码登录要持有分钟级的登录态页面，挂在它上面会被它的 restart 打断，也可能把抖音 Cookie 带进别的插件的截图上下文。这里只复用它的依赖（puppeteer 包）和 Chromium 路径配置，浏览器实例独立。

**为什么扫码登录要有 `confirmed` 这一档状态** — 手机点「确认登录」时抖音只是把 `redirect_url` 交给网页，`sessionid` 要等网页跳完那一趟才写进 cookie jar，实测差 1~3 秒。收到 confirmed 就立刻去读 Cookie 会读到空的，于是被判成失败。所以 confirmed 是独立一档：切状态、记时刻，交给主循环在 25 秒宽限期内轮询 Cookie，拿到就成功，拿不到就说清楚是抖音追加了验证而不是含糊地报超时。

**为什么登录页只拦推荐流、不拦图片字体** — 这里改过一次方向。原来是整片关掉拦截，理由是「命中的都是纯上报，passport 链一个都不在里面，省这几十个请求收益为零」——收益其实是负的：未登录访问首页会被带到 `/jingxuan`，HTML 1.6MB、几十张图、推荐流视频在后台解码，抖音自己的 passport 链要和它们抢渲染进程主线程，实测排队 46 秒才走到 `challenge`，插件在 45 秒上限判死，等于在二维码到手前一秒把页面关了。`BLOCKED_URL_PARTS` 里那三条 feed 接口正是 `/jingxuan` 的数据源，拦掉它页面就没有视频卡片可渲染，登录弹窗的布局一点不受影响。图片和字体仍然放行——二维码弹窗的可见性判定依赖真实尺寸，缺图缺字体时元素容易塌成 0×0 被判死。至于原来担心的「以后清单里多一条命中 passport 的规则就会静默挂掉整条登录链」，改用 `ALWAYS_ALLOW_PARTS` 白名单兜住（passport / qrcode / qrconnect / ttwid / sso 永不拦，且判定顺序在黑名单之前），比整片关掉更准。

**为什么扫码登录没嵌入现成项目** — 备选项要么自带一整套浏览器栈（Playwright，本仓库没装），要么是 Rust/Java 独立进程，要么走逆向签名接口。而抖音扫码本身就是两个公开接口：`get_qrcode` 出图、`check_qrconnect` 出状态，在我们自己的 puppeteer 会话里拦这两个响应就能拿到二维码和结果，Cookie 直接落在同一个 browserContext 里，不需要第二套浏览器或新依赖。

**为什么必须改 UA** — 无头 Chromium 自报的 UA 里带 `HeadlessChrome`，抖音直接返回标题为「验证码中间页」的 4KB 空页；换成 `Chrome` 后同一份代码拿到的是完整首页（1.4MB，登录面板自动弹出）。这里不硬编码某个 UA 字符串，而是取浏览器自报的 UA 只替换这一个词——写死的版本号会随时间变旧，反而更容易被识别，而且平台信息与真实内核不一致也是特征。

**为什么不去点「登录」按钮** — 原本的做法是找文本为「登录」的叶子节点再逐层往上点，抖音改一次 DOM 就失效。实际上未登录访问首页时抖音自己就会弹出扫码面板，插件只需要等：先等「扫码登录/验证码登录/密码登录」这组文字或二维码 img 出现，等不到才退回主动点击。少一个对页面结构的依赖。

**为什么多账号是串行跑** — 并行会同时开多个 Chromium，既吃内存又容易触发抖音风控。

**为什么 puppeteer 的调用要探测再用** — Yunzai 根 `package.json` 里 puppeteer 写的是 `"*"`，实际装到哪个大版本取决于用户机器，而这几个 API 各改过一次名字或位置：

| 用途 | 新 API | 旧 API |
| --- | --- | --- |
| 建隔离上下文 | `browser.createBrowserContext()`（v22+） | `createIncognitoBrowserContext()` |
| 写 Cookie | `context.setCookie()`（v23+） | `page.setCookie()` |
| 读 Cookie | `context.cookies()`（v23+） | CDP `Network.getAllCookies` |
| 连接状态 | `browser.connected`（v22+） | `browser.isConnected()` |
| 取 iframe 的宿主元素 | `frame.frameElement()`（v21 已有，v19 没有） | 在父框架里遍历 `iframe` 用 `contentFrame()` 认 |

写死新 API 在装了旧版的机器上就是 `createBrowserContext is not a function`，所以 `lib/browser.js` 顶部有一层探测分派。读 Cookie 的旧路径特意走 CDP 而不是 `page.cookies()`：后者只返回当前 URL 域下的 Cookie，而扫码会在 `douyin.com` 与 `sso.douyin.com` 之间跳，漏子域等于丢 `sessionid`。

版本一栏写的是**实测出来的边界**，不是从 changelog 抄的：pnpm store 里同时躺着 `puppeteer-core` 的 19.0.0 / 19.11.1 / 21.11.0 / 23.10.1 四份，`frameElement` 在前两份里都没有、后两份里有，所以判定为「v20~v21 之间进来的」。这几个版本号会随着谁的机器上装了什么而变，探测分派本身不依赖它们——写在表里只是为了让下一个人知道这条边界是怎么来的。

**为什么 `index.js` 只做导入** — loader 的 `getPlugins()` 见到插件目录里有 `index.js` 就只导入它并跳过其余 .js（`lib/plugins/loader.js:56`），所以指令想拆文件必须由 index.js 自己扫 `apps/` 并导出 `apps` 对象（`importPlugin()` 会把 `app.apps` 摊平）。键名用 `文件名.导出名`，一个文件里放多个插件类也不会互相覆盖。

**为什么 `applyConfigChange` 写成箭头函数** — loader 只用 `if (!p?.prototype) return` 过滤非插件导出，普通 `function` 有 prototype，会被当成插件类 new 两次然后读 `rule.length` 报错。箭头函数没有 prototype，正好被过滤掉。

**为什么文件登录单开一条指令** — 复用 `#抖音手动登录` 的话，它的正则会把后续参数吞进 Cookie 位置。而 loader 的 context hook 优先于 rule 匹配（`loader.js:205`），`#抖音文件登录 账号名` 挂上下文后用户发的下一条消息（带 `e.file`）会直接进回调，语义更干净。

**为什么锅巴删账号靠快照对比** — GSubForm 删卡片在前端就是把那一项从数组里 splice 掉，提交上来只是「少了一行」，光看内容分不清「用户删了它」还是「它是保存期间新扫码进来的」。所以把发给锅巴那一刻的账号 id 记成快照，只有当时在、这次不在的才算删除。另外锅巴的 `handleFormValues` 会把空数组字段整个丢掉，删光所有卡片时收到的是 `undefined` 而不是 `[]`，所以按 `data.accounts || []` 处理——用 `"accounts" in data` 判断的话最后一个账号永远删不掉。

**为什么远程验证不复用面板会话** — 面板会话一建立就能选机器人、增删账号、改配置、看审计，那是「管理整套插件」的权限。而验证链接只有一个用途：让人把抖音那道身份验证点过去。两者权限差一个数量级，链接又要落在公网可达的地址上，混用等于把管理面板的钥匙塞进一次性验证链接里。所以票据（`lib/remote.js`）、路由（`/api/verify/*`，绕开 `requireAuth`）、页面（`web/verify.html`，独立单文件、不引 app.js、没有任何通往面板的入口）全部另开一套。

**为什么远程操作只转发物理动作** — 只支持点、双击、拖、滚、打字、七个功能键，不提供 `evaluate` 之类能跑任意脚本的入口。那等于把远程代码执行开在公网上，而过一道验证根本用不到它。同理不做通用键盘：`ALLOWED_KEYS` 只放通过验证真正需要的那几个。

**为什么手势要 pointer / touch / mouse 三套一起挂** — 这里改过一次方向。原来按能力挑一套（有 `window.PointerEvent` 就只用 pointer，否则退 touch，再退 mouse），理由是「三套一起挂会把同一次点击发两遍」。实际两头都会踩空：验证链接是从 QQ 私信里点开的，落在哪个内核完全不可控，而「有 `PointerEvent` 这个构造函数」不等于「真的派发 `pointerdown`」——内置浏览器里存在前者有后者不发的组合，那时整块画面点下去毫无反应，也不会有任何报错，与用户报的现象一模一样；反过来「`ontouchstart` in window」在带触摸屏的 Windows 笔记本上同样为真，可那里的人是用鼠标操作的，只挂 touch 就拖不动滑块。所以三套全挂，用一个 `owner` 变量去重：谁先接管这次手势就由谁负责到底，另外两条看到 `owner` 已被占直接返回（派发顺序天然是 pointerdown → touchstart → mousedown，能力最强的那条先到）。末尾再留一层 `click` 兜底 —— 它是所有内核都一定会派发的事件，用来救「down 派发了但 up 和 cancel 一起被吞」这种手势永远收不了尾的情况；靠 `owner` 是否还占着来分辨自己该发还是该让路，正常内核上不会重复发送。

**为什么画面下面要留一行「最近一次操作」** — 这个页面唯一的反馈是那张一秒一换的截图，而「点了但请求没发出去」和「发出去了但抖音弹窗没动」在画面上长得完全一样，出问题时除了猜没有别的办法。所以每个动作都在那行写一句「已送达远端 / 失败：原因」，把故障切成三段：没有这行字 = 浏览器没派发事件；「已送达远端」而画面不动 = 远端点了但页面没响应；「失败」= 括号里就是原因。只写动作类型、归一化坐标与字数，输入的内容一个字都不显示 —— 那里面可能是短信验证码。

**为什么 `pointerdown` 里去掉了 `preventDefault()`** — 它本来是用来挡图片拖拽和长按菜单的，但这两件事 CSS 已经管住了（`user-select` / `-webkit-user-drag` / `-webkit-touch-callout`），而在部分内核上它会连带取消后续的 `pointerup`，正好造出「按下有反应、抬起没动作」。touch 分支仍然自己调 `preventDefault()`：老内核不一定认 `touch-action: none`，不拦掉页面就跟着手指滚，滑块轨迹拖不出来。

**为什么坐标传 0~1 而不是像素** — 前端那张图会被 CSS 缩放（手机屏幕比 1280 窄得多），一旦两边对缩放比的理解差一点点，点击就会偏——而偏一点点在「验证码输入框」和「换一张」之间就是天壤之别。归一化之后前端只需要 `offsetX / 元素宽度`，服务端只需要按同一张图的尺寸还原，中间少一个必须两边对齐的约定。

**为什么截图要显式传 `captureBeyondViewport: false`** — 防的是「图和视口不是一个尺寸」这类故障：一旦截出来的是**整页高**（抖音登录页实测 1280x6000）而报给前端的 `width/height` 还是视口的 1280x800，前端按图的显示尺寸归一化、服务端拿视口当乘数，y 方向就整体错位。而抖音那个身份验证弹窗是 `position: fixed` 居中的，在整页图里被画在文档中部（滚到 2500px 时落在第 2947 行），于是相对 y 是 `2947/6000 ≈ 0.49`，乘 800 得到 393 —— 真实按钮在 447，偏了 54px，正好落在弹窗的空白处。症状极其安静：坐标「合法」、`page.mouse.click` 1~3ms 成功返回、画面纹丝不动。

这条注释里的版本归因**改过一次**，因为原来那句（「v22 以前默认 true，服务器上装的正是 13.7.0」）是错的，而且错进了 git 历史。三层核实的结果：

- **版本**：本地 puppeteer 23.10.1 / Node v25.2.1，服务器容器 24.34.0 / Node v26.8.1 / Chromium 152.0.7977.64。服务器 pnpm store 里只有 `puppeteer-core` 的 19.11.1 / 21.11.0 / 24.34.0，**没有任何 13.x**
- **源码**：19.11.1 / 21.11.0 / 23.10.1 / 24.34.0 的 `screenshot()` 虽然都写着 `captureBeyondViewport ??= true`，但紧接着有一个 else 分支——**既不传 `fullPage` 也不传 `clip` 时强制改回 false**。只有 19.0.0 没有那个分支，`true` 原样交给 CDP
- **真机实测**（6000px 高的页面 + `position:fixed` 弹窗，滚到 2500px，读 JPEG 头里的真实宽高）：

  | 版本 | 什么都不传 | 显式 `false` | 显式 `true` | `fullPage: true` |
  | --- | --- | --- | --- | --- |
  | 23.10.1 | 1280x800 | 1280x800 | 1280x800 | 1280x6000 |
  | 19.0.0 | **1280x6000** | 1280x800 | — | — |

所以：整页图这个故障真实存在，但触发线在 **19.0.0 → 19.11.1 之间**（那个 else 分支进来的地方），不是「v22 以前」；服务器的 24.34.0 与本地的 23.10.1 默认行为完全一致，都按视口截，**两边都不在受影响范围内**。显式传 `false` 各版本都接受、无害，作为对 19.0.0 及更早的防线保留。

诚实地说一句：那次远程验证点击落空的**真实根因因此尚未确定**。修好它的那次提交同时动了 6 处（显式传 `false`、新增 `jpegSize()`、`lastFrame` 记基准、`toPixel()` 认整页图、`describeHit()` 命中探针、click 前先 move 并停 90ms、`viewportSize()` 改从页面实测 `innerWidth/innerHeight`），真正起作用的很可能是后面几条。下次再遇到类似现象，别先怀疑截图基准。

配套那两道防线仍然值钱，而且价值和版本无关：`snapshot()` 每帧解一次 JPEG 头量出图的真实尺寸，和视口不符就按图的尺寸报给前端并 `log("warn")` 喊一声；`toPixel()` 认「图比视口大 = 那是整页图」，先落到图的像素上再减掉滚动量换回视口坐标。它们把「两边对同一个数的理解不一致」从静默错位变成一行警告。

**为什么点击不用 `page.mouse.click()`** — 那个方法是「同一 tick 里 move→down→up」：只产生一个 `mousemove`，按下与松开间隔 0ms。真人点击是一串移动、hover 停一下、按住 50~120ms 再松。抖音这个验证组件（React）把响应挂在 hover 之后才建立的状态上，而 0ms 的按下-松开在不少组件里走不完一轮判定，同时也是最典型的自动化特征。所以这里拆成 `approach()`（分 6 步挪过去）→ 停 90ms → `down` → 停 70ms → `up`，代价是每次点击多 160ms，人察觉不到。

**为什么每次点击都带探针，而不是只在 debug 时带** — 「点击已送达、耗时 2ms、坐标核对无误、画面纹丝不动」这个现象，光看服务端日志永远查不下去：CDP 的 `Input.dispatchMouseEvent` 由浏览器进程受理后立刻 ack，它只保证「事件发出去了」，不保证「有元素收下了」，更不保证「组件理了」。所以点击前在 window 的**捕获阶段**挂一圈监听（捕获是派发链最前面，任何 `stopPropagation` 都挡不住）并开一个 `MutationObserver`，点完读回来，一次性把三件事分开：

- 事件到没到 DOM —— 捕获监听有没有记录
- 到的坐标对不对 —— 记的是事件自己的 `clientX/clientY`，和我们发的那个点一比就知道坐标空间有没有错位
- 组件理没理 —— 面板那一块 DOM 有没有变化（React 只要 `setState` 就一定会动 DOM）

`MutationObserver` 只盯验证面板那一棵子树，不盯整页：遮罩后面那张抖音页还在放视频、转轮播，盯整页的话变化数永远不为 0，「组件理没理」这一问就永远问不出来。

**为什么真鼠标之后还留一条合成事件兜底** — 真鼠标事件要从浏览器进程走到渲染进程，经过一串坐标换算与命中测试，中间任何一环对不上，服务端看到的都只是「静默成功」。人在那边等着把验证过掉，不能因为这条链路上某个环节今天不通就整个功能不可用。所以探针报「面板 DOM 一处没动」时，`forceClick()` 在**落点元素**上补一轮 `pointerdown/mousedown/pointerup/mouseup/click`。

这不是「执行任意脚本」那个口子：作用对象由页面自己的 `elementFromPoint` 决定，调用方递不进来选择器也递不进来代码。合成事件的 `isTrusted` 是 `false`，React 不看这个字段所以照样触发；真只认可信事件的组件这条兜底帮不上，但那种情况日志里会留下痕迹。

判据分两层：**事件没进 DOM 就一定补**（此时组件压根没收到，DOM 在不在动都与我们无关），事件进了才退回看「面板 DOM 有没有动」。不能只看 DOM，因为抖音那个验证码框旁边挂着「49s后重新发送」的倒计时，它每秒改一次 input 的属性，于是面板里永远有变化——现场就是这么卡住的：探针报「DOM 变化 4 处（首条 attributes 于 `input#button-input`）」，而那四处全是倒计时，我们的点击一个都没到，兜底却被这个假信号挡住没出手。

**为什么打字也要一条兜底，而且是三种不同写法** — `page.keyboard.type()` 走的是 `Input.dispatchKeyEvent`，和鼠标同一条通道：鼠标事件到不了 DOM 的现场，键盘事件同样到不了。更麻烦的是键盘事件没有坐标，它只往「当前有焦点的那个元素」上送，所以现场表现是双重的——点输入框那一下焦点没换过去（焦点是浏览器处理 `mousedown` 默认行为时给的，而 `mousedown` 没到 DOM），紧接着六个按键发进了空气，日志里却是两条漂亮的「已送达」。

三处不能省的细节，少一处 React 就不认这次输入：

- **用原型上的 value setter 写值**。React 把 input 的 `value` 劫持成自己的，直接 `el.value = x` 只改到它那个副本，内部记录（`_valueTracker`）跟着同步更新，于是随后的 `input` 事件被 `updateValueIfChanged` 判成「值没变」丢弃。要用 `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, "value").set` 绕过劫持写到真正的 DOM 属性上。
- **`InputEvent` 而不是 `Event`**。React 17+ 靠 `data` / `inputType` 区分输入种类，普通 `Event` 在部分受控组件里拿不到值。
- **一个字符一轮**，而不是整串塞进去。抖音这个验证码框每满一位就判一次（满 6 位自动提交），整串塞进去它只会看到最后一次变化，中间那几步状态跳空。

配套还有两处：点击落在 `input/textarea/[contenteditable]` 上时无条件 `el.focus({ preventScroll: true })` 把光标放进去（`preventScroll` 是因为弹窗是 `fixed` 的，聚焦时让页面滚起来会让坐标基准跟着变）；打字前后各读一次那个框的**长度**（不读内容——里面装的可能就是短信验证码），一点没变才补，因为满 6 位自动提交后长度会回到 0，那不是失败。

按键（`Enter`/`Backspace` 等七个）一律真键盘 + 合成各来一遍，不做「先试真的、不行再补」：这几个键的效果判不出来（`Enter` 是提交、`Escape` 是关弹窗、方向键只挪光标，都没有一个前后对比就能知道成没成的读数），而重复一次的代价很低，漏掉一次的代价是用户点了没反应只能干等超时。删除键例外，它会真的少删一个字，所以按内容长度判。

**为什么要开焦点模拟** — 无头浏览器里没有窗口管理器，页面的 `document.hasFocus()` 常年是 `false`。大多数点击不受影响，但焦点相关的组件（输入框拿不到 caret）会，把 `hasFocus` 当自动化特征看的脚本也会。第一次动作时用 CDP 的 `Emulation.setFocusEmulationEnabled` 打开（每页一次），失败一律咽掉 —— 它是加分项不是必要条件。

**为什么页面全关完之后要收掉浏览器实例** — 一个开着抖音页面的 Chromium 占 200~400MB，而续火一天只跑一次、扫码登录更少；实例常驻的话那份内存会一直留到 Yunzai 重启。所以监听 `targetdestroyed`，在「已经没有真实页面」（`about:blank` 是启动自带的，不算）时延时 `spark.browserIdleClose` 秒关掉整个实例。

挂在浏览器事件上而不是改各个调用点，是因为关页面的地方有五处（登录 cleanup、续火三处、`openPage` 的失败回滚），漏一处这条路就是废的；而「最后一个页面没了」这个事实只有浏览器自己最清楚。延时不能取 0：续火是一个账号一个页面串着跑，页面之间有几秒空档，立刻关掉就变成每个账号都重启一次浏览器，启动那两三秒比省下来的内存值钱。`openPage()` 开头会把倒数中的定时器撤掉，空档里又来活时不会被上一轮误关。

启动参数里另有一组省内存的（`MEMORY_ARGS`），最值钱的是 `--autoplay-policy=user-gesture-required`：视频一起播，解码缓冲区几十上百 MB 就出去了，而我们只要 DOM 文本和按钮位置，一帧画面都不用看——资源拦截只拦得住 `media` 类型的**请求**，拦不住已经在页面里的 `<video>` 自己起播。三条明确没放进去：`--js-flags=--max-old-space-size=N`（划小了抖音前端会把堆撑爆，渲染进程直接崩，表现是莫名白屏）、`--single-process`（省内存最多，但会让多个账号共用渲染进程，账号隔离是这个插件的地基）、`--disable-images`（图片拦截已按场景分开做了，登录页不拦是因为二维码弹窗的可见性判定要真实布局）。

**为什么退出收尾只包 `Bot.restart`，不自己挂信号** — 因为四个信号那条路 puppeteer 已经做了，而且做得比我们能做的更彻底：它在 `process.on('exit')` 与 SIGINT/SIGTERM/SIGHUP 上都挂了 `kill()`，非 win32 直接 `process.kill(-pid, 'SIGKILL')` 连整个进程组一起杀（Chromium 是新进程组的组长，下面还挂着 renderer / gpu / zygote 一串，只杀组长的话那一串会被 init 收养留下来）。重复挂一遍只会让收尾路径变成两条互相不知道对方存在的分支。

真正漏掉的是 `lib/bot.js` 的 `process.execve`：它在内核层替换进程镜像，不走 `process.reallyExit`，**exit 钩子一个都不跑**（`execve` 的 JS 实现只做参数校验 → 诊断通道 publish → `_execve`，没有任何 `emit('exit')`）。而服务器用 `node app start` 起，`start_type` 是 external，`Bot.restart()` 第一件事就是它。于是 puppeteer 的清理不触发、进程组不被杀，换完镜像的新 Node 又压根不认识这些子进程 —— pid 还是原来那个，从外面看「重启成功了」，实际每次多留一个 Chromium 和一个 `puppeteer_dev_chrome_profile-*` 目录。现场数据：服务器攒到 31 个（最老的来自 2025-10-09），本地 `%TEMP%` 也有 10 个。

`process.on("exit")` 那层仍然留着，但只作兜底、只跑同步代码 —— Node 在 exit 钩子里不会等任何 Promise，写 `async` 只会让人误以为收尾做完了。它真正收的是 sqlite（`DatabaseSync.close()` 是同步的），`#关机`（`Bot.exit` → `process.exit(255)`）走的就是这条。

改 `Bot.restart` 本身有个坑：`global.Bot` 是 `new Proxy(this.bots, { get })`，**只有 get 陷阱**。写操作直接落在被代理的 `this.bots` 上（`Bot[uin]` 就是这么存的），读却仍旧优先走 `this[prop]`，于是 `Bot.restart = fn` 赋值成功、调用时拿到的还是原来那个（实测确认过）。真身在 `bot = this` 这个字段上，必须先取 `global.Bot.bot` 再改。取不到就不包并 `log("warn")` —— 宁可不收尾，也不能在插件加载期把 Yunzai 搞崩。

预算这么定：关页面合计 4 秒（用户正盯着 `#重启`，一个卡住的 `page.close()` 不该把重启变成「机器人没反应」，超了就直接往下走，反正 `browser.close()` 会把这些页面一起带走），关浏览器单独 6 秒且不与前面共享（`BrowserLauncher.closeBrowser` 先试 CDP 优雅关闭，**5 秒**没关掉才转 SIGKILL，给少了就总是走到我们自己的强杀分支）。收尾顺序也有讲究：先摘定时任务，否则收到一半又起一轮续火把刚关掉的浏览器重新拉起来；最后才关库，因为聊天会话关闭时还会往库里写最后几条。

**为什么聊天要常开一个页面，而不是像续火那样开完就关** — 续火是一次性任务（进去、发完、走），而聊天要能看到对方回了什么。每次轮询都重开一个 Chromium、登录、等会话渲染，一轮就是十几秒；更要紧的是每一轮都是一次**新的登录会话**，抖音那边看到的是「你每分钟登录一次」，这比长期挂着一个会话可疑得多。

代价是三条约束都得自己扛：和续火抢同一把账号锁（同一份 Cookie 活在两个 BrowserContext 里就是两个并发登录）、自己管空闲超时（`browser.js` 的自动收浏览器判据是「还有没有真实页面」，聊天页开着永远不触发）、以及只能靠纯文本认消息（抖音不给消息 id，而 `image/media/font` 默认被拦，头像本来也加载不了）。这三条的处理都在「私信聊天」一节。

**为什么聊天记录用 `node:sqlite`，而不是现成的那几个** — 挨个试过：`better-sqlite3` 虽然躺在 Yunzai 的 `node_modules` 里（传递依赖），但 `require` 直接失败（`bindings.js` 找不到 `file-uri-to-path`）；根 `package.json` 声明的 `sqlite3` 在运行容器里 require 不到；`Bot.getMap()`（LevelDB）打开时会把整表 `for-await` 读进内存，聊天历史不适合；redis 重启就没了，而用户明确要求会话不过期。`node:sqlite` 是内置模块、零新依赖，容器里实测 WAL 可开、5000 行事务写入 10ms。

代价是它要 Node ≥ 22.5，所以取不到时整块降级成「不落盘」而不是报错。这里有个细节不能省：用 `createRequire(import.meta.url)("node:sqlite")` 而不是顶层 `import "node:sqlite"` —— 顶层 import 一个不存在的内置模块会让整个文件加载失败，那就不是降级而是把插件一起带走了。也没用 `await import`，因为本模块所有导出都是同步的，不想为了打开数据库把 API 全变 async。

**为什么 `#抖音web下线` 要连登录会话一起终止** — 以前它只清票据（链接打不开了），但那个登录会话还活着：浏览器页面开着占内存，超时兜底也还挂着，于是人早就下线了，十分钟后照旧收到一句「❌ 抖音要求的验证在 10 分 0 秒内没有完成」——既没用，又让人以为下线没成功。现在走 `cancelUserSessions()` 把会话打到 `canceled` 终态，`cleanup` 顺手 `clearTimeout` 摘掉定时器；超时与失败两条兜底进门都先看状态（`["success","failed","canceled"].includes`），所以即使有一路已经在半途也不会再往外推消息。下线本身那句提示指令在哪发就回哪，群里发的群里可见。

**为什么拖动要连时间戳一起重放** — 滑块验证判的就是那条曲线，代码生成的匀速直线基本过不去。前端录的是用户真手拖出来的轨迹（含每点的相对时刻），服务端用 `page.mouse.move()` 按原节奏逐点重放，过的是真人轨迹。单步间隔夹在 0~120ms：既保住真实节奏，也不让一条轨迹把请求拖到几分钟。

**为什么帧用 jpeg 不用 png** — 同一帧 png 约 300KB、jpeg 质量 60 约 40KB。前端每秒拉一张，差出来的带宽在公网反代下很明显，而这张图只是给人看清按钮在哪，不需要无损。

**为什么登录结束不立刻撕票** — 页面就在人手上开着，验证刚点完那一秒后端就把票撕了的话，前端下一次拉帧收到的是 401「链接失效」，而真实结果恰恰是「Cookie 已存好了」。所以 `closeBySession` 只标记收尾并把期限压到 1 分钟，让页面把最终结论读到手；这段窗口里取帧和操作都会因为 page 已关闭而失败，读不到别的东西。

**为什么更新前要备份整个 `config/` 与 `data/`** — 参考实现只备份单个 yaml，但本插件 `data/secret.key` 一旦被 `git reset --hard` 冲掉，所有已保存的 Cookie 都永久解不开。恢复时只写回「pull 后不存在」的文件，不覆盖新代码带来的内容。

**为什么找好友要分四档匹配** — 抖音的会话项和搜索结果项里没有「昵称」这个能单独选中的元素：一条会话读出来是 `主号19:0310分钟内在线`，昵称、最后活跃时间、在线状态挤在一起；搜索结果里昵称还会被高亮拆成一个字一个 `<em>`。原来的判据是「某个后代元素的 textContent 正好等于名字」，这两种形态一个都比不上——现场那句「搜「主号」未命中：结果 1 条」就是它，人明明搜出来了。现在从严到松试四档：完全相同 → 去掉时间/在线状态后相同 → 单个叶子文本包含 → 整条文本包含（昵称被拆散时只有它还是连着的），命中用的是哪一档会记进日志，下次一眼能看出是哪种形变。名字先过一遍 NFKC 折全角（昵称里全角字母很常见，而人在面板上打的是半角）并去掉零宽字符（挂件昵称的常客，肉眼看不见但让 `===` 直接失败）。

两档松的（包含匹配）额外做歧义保护：同一档同时套住不止一条就一律判未命中，比如找「主号」而列表里还有「主号2」。发错人比不发严重得多，而这时用户把名字写全就能自己解开。严档不做这个检查——名字都一模一样了，多命中一条只能是抖音把同一会话渲染了两遍。另外读文本时顺手给每项打一个 `data-dy-slot` 序号，回来按属性取元素句柄：抖音的列表随时重渲染，按「第 N 个」二次查询很容易错位，而错位就是发错人。

**为什么定位「一条会话」用「兄弟最多」而不是认时间戳或 class 名** — `[class*="conversation"]` 是模糊匹配，一条会话从外层容器到里面的标题行、时间格子每一层 class 都带 conversation，于是同一个好友被数成十几个节点：现场「读到 5 个昵称」其实只有一个好友，面板上并排列出的 `主号19:0310分钟内在线` / `主号19:03` / `主号` / `19:03` / `10分钟内在线` 就是它的五个嵌套层级。光取最外层也不行，那是整张列表，几个好友会被并成一条。试过两条路都不行：**认时间戳**（「每条会话必然带一个 19:03」）在只有一个真会话时整张列表也只带一个时间，分不出容器和行，而「互动消息」这类系统入口压根没有时间；**认 class 串相同**会被「当前选中行挂的额外 active class」打穿，那一行被单独分出去。最终用纯结构判据：把所有命中节点按父节点归组，会话行是一批同父兄弟而各层容器每种只有一个，所以成员最多的那组就是会话行，数量相同时取更靠外的那层。不认 class 名也不认任何中文文案，抖音改文案改样式都不影响。

**为什么搜索之后还要加一条会话列表兜底** — 搜「又在說我壞話」抖音返回 0 条，而那个会话就明明白白挂在左侧列表里（面板的「拉取好友会话列表」按钮读到的就是它）。抖音的搜索索引对繁体、emoji、刚改的备注名都不可靠，而列表是当前登录态直接渲染出来的，反而更可信。兜底放在搜索之后而不是之前：列表只有前几十条（要滚动才加载更多），搜索才是覆盖全量好友的那条路，所以先搜、搜不到再翻列表。顺带把等旧结果收起的上限从 5 秒压到 1.5 秒（`SEARCH_CLEAR_TIMEOUT`）——抖音的搜索面板在输入框获得焦点时就挂出「最近会话」，清空输入并不会让它消失，于是每个候选名都在这里白等满 5 秒、三轮重试就是 15 秒；而残留项本身不危险，匹配是按名字挑的，上一个候选名的残留不会被当成这一个。

**为什么消息输入框的选择器要分四档** — 原来只认一条 `.messageEditorimChatEditorContainer [data-slate-editor="true"][contenteditable="true"]`，而开头那个 class 是抖音打包生成的混淆串，发一次版就可能改名。现场那句 `Waiting for selector ... failed` 就是它：会话已经打开、输入框也在页面上，只是外层容器不叫这个名字了，于是等满 12 秒、当次「发送 0 条」。现在从严到松四档（混淆容器内的 Slate 编辑器 → 任意 Slate 编辑器 → class 含 ChatEditor 的可编辑区 → 页面上任何可见的 `contenteditable`），一轮里四档全问一遍、问不到等 400ms 再来一轮，总上限还是 12 秒，不是「4 档各等 12 秒」。最后一档确实宽，但抖音聊天页除了消息输入框没有别的可编辑区域，而「宽一点」最坏是消息发不出去，「严一点」是版本一变整个功能不可用。命中的是哪一档写进 debug 日志，改版时一眼能看出来。

**为什么点击抽成 `lib/interact.js` 而不是各处 `el.click()`** — 这三处点击（远程验证页转发过来的手势、续火点「发消息」、自动登录点「发送验证码」）遇到的是同一类静默失败：`handle.click()` / `el.click()` 都只保证「事件发出去了」，不保证有元素收下、更不保证 React 组件理了，而抖音那几个组件恰好都需要 hover 之后才建立状态。之前是远程验证那边独有一套 approach + 探针 + 合成事件兜底，续火和登录各自裸调 puppeteer，于是同一个坑修一遍只修好三分之一 —— 续火「点了发消息但会话没开」查了两轮才发现根因和远程验证那条一模一样。现在真鼠标靠近、hover、按住 70ms、捕获阶段探针、`MutationObserver`、合成事件兜底、输入框自动聚焦全在 `interact.js` 里，三处共用，判据只有一份。

**为什么 `sendCharacter` 之后还要读一遍编辑器里有多少字** — 它走 CDP 的 `Input.insertText`，焦点没在编辑器里时**照样返回成功**，紧接着那下 Enter 就在空会话里敲了个回车，结果是「日志说发了 N 条，抖音那边一条没有」。这是最坏的一种失败：不报错、不留痕。所以发送前读一眼编辑器的文本长度，空的就补一轮合成输入（Slate 要 `beforeinput` + `input` 才认字）。读长度不读内容 —— 自定义发信的正文是用户自己写的，没必要进日志。

**为什么群里默认给链接打码** — 面板地址对很多人就是 `http://公网IP:2536`，而 `#抖音登录`、`#抖音web上线` 这些指令在群里发时回复也落在群里，等于把一台开着管理面板的机器的地址念给全群听。所以 `web.maskLinkInGroup` 默认开，群消息里把**主机名与端口**一起打码（协议与路径留着，看得出这是哪个功能），完整地址改由私信发。有域名、或者面板本来就打算公开的可以关掉，指令照旧能用。打码只作用于群消息这一层，私信始终是完整地址 —— 否则用户拿到一条打了码的链接根本没法点。

端口原来是留着原文的，理由是「没有主机的端口号不指向任何东西」。那个推理漏了两件事：主机尾 3 位加上端口，配合群里能看到的其它信息（别的插件打印过的地址、IP 段）就够拼出一个可扫的目标；而 Yunzai 默认端口 2536 本身就是指纹，露出来等于告诉别人「这是台 Yunzai，去试它的其它路由」。现在整段打掉只留位数，位数是给本人对照用的。实现上有个坑：不能写成 `maskSecret(port, 0, 0)` —— 它内部 `slice(-tail)`，而 `slice(-0)` 等于 `slice(0)`，会把整个端口原样吐回来。

**为什么面板验证码放 URL 的 hash 而不是 query** — 想要的效果是「点一下就进面板」，不用在两条消息之间来回复制 6 位码。但 `?ABCD` 这种写法会把码交给服务端：Yunzai 的 `serverHandle` 会把 `req.query` 整个打进日志（`lib/bot.js`），而排查问题时大家习惯直接把 `logs/command.*.log` 贴出来 —— 那等于把一个还没过期的验证码贴到公开的地方。hash 压根不发给服务端，因此不进 access log、不随 Referer 外泄，前端读完立刻 `replaceState` 抹掉，地址栏、书签、截图里也不留。这条路远程验证页面（`/verify#t=xxx`）已经跑了很久，QQ 能正常识别带 hash 的链接。私信里同时给出地址与 6 位码，链接点不开时还能手输。

**为什么自动短信排在远程验证页面之前** — 远程验证页那条路是通用兜底：截图、票据、公网地址、用户在手机浏览器上一路点。而扫码后追加的验证里最常见的一种（「身份验证 → 接收短信验证码 → 发送验证码」）**没有一步是只有人能做的**：按钮位置固定、文案多年没动，点完只是让抖音往绑定手机发一条短信。真正只有用户能提供的东西是那 6 位数字本身。既然模拟点击那一整套已经写好了，就让插件把「点」全部做完，只跟用户要数字 —— 省掉一个公网地址的暴露面，也省掉用户在小屏幕上对着 1280 宽的截图点按钮。所以 `markVerify` 先试 `tryAutoSms()`，任何一步不成立才落回票据那条路。滑块、拼图、要求绑定手机号进门就直接返回 false：那些是真需要人来过的。

**为什么 `tryAutoSms` 必须先确认「已发送」再跟用户要码** — 否则失败方式很难看：插件说「请把验证码发我」，用户盯着手机等一条永远不来的短信，直到 10 分钟超时。而「发送验证码」这一下没点着的原因可能只是抖音换了文案。所以点完之后 `waitForFunction` 8 秒等页面上出现「验证码已发送 / 重新发送 / 倒计时」，等不到就当整条路不成立、回落远程验证页面 —— 宁可让用户点一个链接，也不要让他等一条不存在的短信。同理 `s.smsAsked` 是一次性的：抖音对发短信有频率限制，主循环每 2 秒转一圈，多点一次可能把手机号锁掉。

**为什么「已发送」的正则里那个「后」不能省** — 判据原来写成 `\d+\s?s\s?(后)?`，「后」是可选的。而这个页面背后就是抖音首页推荐流，视频卡片上挂着「15s」这种时长标注，`document.body.innerText` 一读就撞上，于是插件在**还没点「发送验证码」**的时候就认为短信已经发出去了，直接跳到跟用户要码 —— 正是上一条要防的那个失败。改成必须带「后」（`\d+\s?s\s?后`）：倒计时文案一定是「58s 后重新发送」，时长标注不会带这个字。fixture（`15s` 干扰项）复跑确认。这条正则在 `readSmsState` 和 `tryAutoSms` 的 `waitForFunction` 里各有一份，改一处要改两处。
